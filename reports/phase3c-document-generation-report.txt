SCOPE
═══════════════════════════════════════════════════════════════════════════════

Phase 3C builds the document generation foundation for unfair dismissal claims.
The backend and client engine are unchanged. This phase adds:

  1. Template-anchored Particulars of Claim (PoC) generation
  2. Template-anchored Schedule of Loss (SoL) generation
  3. POST /documents/generate endpoint with safety gate
  4. Legal boundary notice in every generated document (verbatim)
  5. safety_check() blocking prohibited phrases before any document is returned
  6. Assessment-to-document mapping from structured pipeline output + intake facts
  7. Document generation UI on the assessment results page
  8. Full intake facts stored in sessionStorage for document generation context

═══════════════════════════════════════════════════════════════════════════════
GENERATION APPROACH — TEMPLATE-ANCHORED (NO FREEFORM LLM)
═══════════════════════════════════════════════════════════════════════════════

All documents are generated by pure Python template filling.
The LLM is NOT invoked during document generation.

Content sources:
  - Structured assessment object (pipeline output from /assess)
    → reasoning_summary, key_weaknesses, employer_arguments,
      deadline_info, value_range, citations, has_viable_claim, strength
  - User intake facts
    → edt, service_start_date, reason_for_dismissal, was_procedure_followed,
      ec_day_a, ec_day_b, weekly_pay
  - [PLACEHOLDER] notation for data not held by lawapp
    → claimant name, employer address, claimant date of birth
    → User fills these in before filing

This approach:
  - Eliminates hallucination risk (no LLM in the loop)
  - Is fully auditable (template source code is the specification)
  - Satisfies the "template-anchored generation only" requirement
  - Allows LLM-expanded narrative in Phase 4+ within template slots

LEGAL BOUNDARY GUARDRAILS — DOCUMENT LAYER
═══════════════════════════════════════════════════════════════════════════════

LEGAL_BOUNDARY_NOTICE (verbatim, in every document, at top and bottom):
  "This document is a SELF-HELP DRAFT prepared using lawapp."
  "It is NOT legal advice. lawapp is not a solicitor or law firm."
  "You must review, verify, and correct this document carefully before filing."
  "lawapp does not file, submit, represent you, or conduct litigation."
  "No outcome is guaranteed."

safety_check() patterns blocked (regex, case-insensitive):
  - "you will win"
  - "guaranteed? (to win|outcome|result|success)"
  - "we guarantee"
  - "we will (file|submit|send) (your|this|the) claim"
  - "we will represent you"
  - "we represent you"
  - "as your solicitor"
  - "acting as your (solicitor|lawyer|legal representative)"
  - "certain(ly)? (succeed|win|prevail)"

If any violation is detected: HTTP 500 returned + error logged.
Since documents are template-generated, violations cannot occur in practice —
the safety check is a belt-and-suspenders guardrail for future modifications.

═══════════════════════════════════════════════════════════════════════════════
API ENDPOINT
═══════════════════════════════════════════════════════════════════════════════

POST /documents/generate
Request:
  {
    "document_type": "particulars_of_claim" | "schedule_of_loss",
    "assessment": { ... },   // full /assess response
    "facts": { ... }         // original intake facts
  }

Response (200):
  {
    "document_type": "particulars_of_claim",
    "title": "Particulars of Claim — Unfair Dismissal (Self-Help Draft)",
    "content": "... full document text ...",
    "safety_check": {"passed": true, "violations": []},
    "generation_method": "template",
    "disclaimer_included": true
  }

Response (422): invalid document_type (Pydantic Literal validation)
Response (500): safety check failed (would indicate a template regression)
