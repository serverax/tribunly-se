SCOPE
═══════════════════════════════════════════════════════════════════════════════

Phase 4B adds four premium bundle components:
  1. Witness statement structure
  2. Chronology of events
  3. Evidence checklist
  4. ET1 support notes

Plus: separate premium payment gate, bundle metadata storage, saved-case
page integration showing bundle status.

═══════════════════════════════════════════════════════════════════════════════
BUNDLE COMPONENTS (backend/engine/bundle.py)
═══════════════════════════════════════════════════════════════════════════════

All components are template-generated. No LLM involvement.
Sources used:
  - case.assessment (structured pipeline output)
  - case.key_dates (EDT, deadline_date, ec_day_a/b, employment_start_date)
  - Confirmed/corrected extracted facts from uploads ONLY

GUARDRAIL: get_confirmed_facts() filters strictly:
  - status must be 'user_confirmed' or 'user_corrected'
  - value must not start with '[Extracted' (placeholder  -  excluded)
  - 'extracted_unconfirmed' and 'rejected' facts are never used

Missing dates: shown as [DATE NOT CONFIRMED]  -  never invented.

1. Witness Statement  -  employment background, timeline, procedure concerns,
   impact/loss, document references. Statement of truth included.
   User must expand narrative sections before filing.

2. Chronology  -  dated event table: employment start, EDT, ACAS Day A/B,
   limitation date. Missing dates explicitly flagged.

3. Evidence Checklist  -  8 categories: contract, dismissal docs,
   disciplinary docs, appeal docs, communications, ACAS cert, witnesses,
   medical (only if relevant). Uploaded documents shown.

4. ET1 Support Notes  -  claim type, parties, key facts, legal summary,
   remedy, deadline warning. Explicitly states lawapp does not file or submit.

═══════════════════════════════════════════════════════════════════════════════
METADATA STORAGE
═══════════════════════════════════════════════════════════════════════════════

When full premium bundle is generated, one row per component is saved:
  documents table: case_id, doc_type={component}, storage_ref='bundle:generated',
                   is_user_upload=false, extraction_status='generated'

GET /cases/{id}/bundle queries this for bundle status.

SAFETY CHECKS
═══════════════════════════════════════════════════════════════════════════════

safety_check() from documents.py applied to every component before return.
Blocks: "we will file", "we will submit", "we will represent", "guaranteed",
        "you will win", "as your solicitor", etc.

Every component includes BUNDLE_BOUNDARY_NOTICE at top and bottom.

═══════════════════════════════════════════════════════════════════════════════
DATA-PROTECTION NOTES
═══════════════════════════════════════════════════════════════════════════════

  - Bundle is generated from: case.assessment (de-identified), case.key_dates,
    and confirmed extracted facts from uploads.
  - PII in extracted facts (employer_name, employee_name) appears in bundle
    only if the user has explicitly confirmed them from uploaded documents.
    These are shown as [YOUR EMPLOYER] / [YOUR FULL NAME] if not confirmed.
  - Bundle content is NOT persisted  -  only metadata (doc_type, timestamps)
    stored in documents table. No bundle text stored in DB.
  - No raw upload content is used in bundle generation.
  - No external API calls.
