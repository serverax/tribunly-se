1. ADMIN AUTHENTICATION
═══════════════════════════════════════════════════════════════════════════════

Mechanism: X-Admin-Key header on all /admin/* endpoints.
Implementation: FastAPI Depends() → _require_admin_key().
Key source: ADMIN_API_KEY environment variable (read at request time).
Behaviour:
  - ADMIN_API_KEY not set → 403 "Admin access is not configured"
  - Wrong key → 403 "Invalid or missing X-Admin-Key header"
  - Correct key → 200

Endpoints protected:
  GET /admin/dp-report
  GET /admin/rules-verification
  GET /admin/production-readiness
  GET /admin/retention-status

GUARDRAIL: Key value never logged. NEVER print or expose the key value.
Limitation: This is an API key, not OAuth/JWT user authentication.
  Full user authentication is Phase 7.

2. ENCRYPTION AT REST
═══════════════════════════════════════════════════════════════════════════════

Module: backend/engine/encryption.py
Algorithm: Fernet (AES-128-CBC + HMAC-SHA256) from cryptography package.
Key source: ENCRYPTION_KEY environment variable (URL-safe base64 Fernet key).

Fields encrypted when ENCRYPTION_KEY is set:
  - handoff_leads: name, email, phone (plaintext replaced by "[encrypted]";
    encrypted ciphertext stored in name_encrypted, email_encrypted, phone_encrypted)
  - Uploaded files: file bytes encrypted before writing to filesystem
  - Upload encryption is transparent to callers (no API change)

New DB columns (migration 012):
  - handoff_leads: name_encrypted, email_encrypted, phone_encrypted, pii_encrypted

API response includes: pii_encrypted: true/false on POST /handoff/leads.

Phase 6 limitations (NOT production-ready for key management):
  - Key in env var  -  no HSM, no KMS, no key rotation
  - Fernet (AES-128-CBC)  -  AES-256-GCM recommended for production
  - Phase 7: HSM integration, key rotation, separate keys per data class
  - cases.facts_encrypted: column exists; not populated in Phase 6
    (assessment jsonb is already de-identified; intake facts not persisted)

3. RETENTION AND DELETION POLICY (Art.17 UK GDPR)
═══════════════════════════════════════════════════════════════════════════════

New endpoints:
  DELETE /cases/{case_id}          -  soft delete; sets deleted_at; 404 on GET
  DELETE /handoff/leads/{lead_id}  -  clears PII fields; sets deleted_at

New DB columns (migration 012):
  - cases: deleted_at timestamptz
  - handoff_leads: deleted_at timestamptz
  - retention_runs: audit log of retention script runs

Admin endpoint:
  GET /admin/retention-status?retention_days=N   -  report old records (no delete)

Script:
  scripts/run_retention.py   -  dry run by default; --apply to execute
  Soft-deletes cases older than RETENTION_CASES_DAYS (default 90)
  Clears PII from handoff leads older than RETENTION_HANDOFF_DAYS (default 30)

GUARDRAIL: Audit logs preserved; only PII cleared. Consent records retained.
GUARDRAIL: run_retention.py is DRY RUN by default  -  require --apply flag.
