2. SECURITY BEHAVIOUR IMPLEMENTED
═══════════════════════════════════════════════════════════════════════════════

  RS256/JWKS verification path (when JWT_JWKS_URL is set):
    Algorithm:   RS256 (via PyJWT RSAAlgorithm.from_jwk)
    Key source:  JWKS endpoint fetched from JWT_JWKS_URL
    Key cache:   5-minute in-memory TTL cache; thread-safe
    Key select:  by kid header claim; fails closed (401) on unknown kid
    Validates:   signature, exp, iss (if JWT_ISSUER), aud (if JWT_AUDIENCE), sub
    Fails closed: JWKS fetch failure → 503; decode error → 401; no silent accept

  Dispatcher routing:
    JWT_JWKS_URL set → RS256/JWKS (production-grade)
    JWT_SECRET set   → HS256 (Phase 6C, dev/test quality)
    Neither          → 503 (server misconfigured)

  What changed for HS256:
    HS256 path (Phase 6C) is preserved unchanged.
    is_auth_production_ready() now correctly marks HS256-only as NOT production-ready.
    Phase 6C test updated to reflect this (Phase 7A is not a regression — it's correct).

  Guaranteed:
    - Token values NEVER logged
    - JWKS URL NEVER logged
    - Sub claim NEVER logged
    - Exception details from PyJWT NOT forwarded to callers
    - JWKS cache never bypasses signature verification
