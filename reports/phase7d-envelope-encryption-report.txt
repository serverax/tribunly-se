2. ENVELOPE ENCRYPTION BEHAVIOUR
═══════════════════════════════════════════════════════════════════════════════

  Encryption path (generate_data_key):
    1. Call KMS.GenerateDataKey(KeyId=ARN, KeySpec="AES_256")
    2. Receive Plaintext (32 bytes) + CiphertextBlob
    3. Derive Fernet key: base64.urlsafe_b64encode(Plaintext[:32])
    4. Use Fernet key TRANSIENTLY for encryption → DISCARD
    5. Persist EncryptedKeyBundle (CiphertextBlob + metadata) with ciphertext
    6. CiphertextBlob is safe (encrypted by KMS master key)

  Decryption path (decrypt_data_key):
    1. Load EncryptedKeyBundle from persisted storage
    2. Call KMS.Decrypt(CiphertextBlob) to recover Plaintext
    3. Derive same Fernet key → use TRANSIENTLY for decryption → DISCARD

  Storage model (DB):
    cases.encryption_key_metadata         = EncryptedKeyBundle JSON (safe to persist)
    handoff_leads.encryption_key_metadata = EncryptedKeyBundle JSON (safe to persist)
    NEITHER column contains plaintext keys.

  Phase 7E+ (not implemented):
    - Integration of generate_data_key into existing Fernet encrypt/decrypt
    - Key rotation lifecycle (re-encrypt with new data key)
    - Batch migration of existing records

  GUARDRAILS verified by tests:
    - Plaintext data keys NEVER in bundle (test 5)
    - Plaintext NEVER in logs during generate (test 13)
    - Plaintext NEVER in logs during decrypt (test 14)
    - Empty CiphertextBlob fails closed (test 11)
    - KMS failures fail closed (tests 8, 12)
